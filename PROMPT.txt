## 3.4 Evidence discipline

Always distinguish among:

* implemented;
* compiled;
* linked;
* built;
* launched;
* tested;
* visually inspected;
* benchmarked;
* verified in CI.

* A successful CMake build is not proof that a platform launches.
* A successful headless smoke test is not proof of visual correctness.
* A CI artifact existing is not proof that it was visually inspected.

Never invent FPS or hardware results.

Never claim WebGPU. The web renderer is bgfx's WebGL2 / OpenGLES backend.

Never claim a platform works unless the required build/run evidence exists.

# 5. Known gaps to investigate and resolve

These were previously verified from the code.

## 5.1 Native shader portability

`Renderer::init` currently allows native bgfx backend selection through `RendererType::Count`.

`cmake/Shaders.cmake` only compiles:

* `glsl`
* `spirv`
* `essl`

and `src/render/shader_library.cpp` maps unsupported backends to `essl`.

Native Windows and macOS therefore require real backend-specific shader handling.

## 5.2 Native asset path

`AAA_ASSET_DIR` is currently an absolute build directory baked into the build.

A packaged binary cannot rely on that path.

## 5.3 Native UI

Existing title, pause, HUD, prompts and notifications are DOM-only.

Native builds need an in-engine equivalent.

## 5.4 bgfx threading

`bgfx::renderFrame()` is currently not called before `bgfx::init`.

Native bgfx therefore defaults to multithreaded mode.

The release should use deterministic single-threaded rendering by explicitly calling `bgfx::renderFrame()` before initialization.

## 5.5 Visual quality

Current character and wolf visuals are rigid procedural parts.

Known environmental issues include:

* flat pine crowns when viewed from below;
* overly lime-looking grass;
* flat distant mountains.

## 5.6 Stale documentation

`tools/sandbox/bootstrap_toolchain.sh` references files that no longer exist.

The browser playtest `default` script presses F3 while the debug overlay now requires `?debug=1`.

## 5.7 Console noise

bgfx emits approximately 20 WebGL `INVALID_ENUM: getInternalformatParameter` messages during startup.

SDL3 uses a deprecated `ScriptProcessorNode`.

These are currently harmless.

Do not patch bgfx merely to hide the WebGL warning unless a robust project-local solution exists.

## 10.4 Wolf presentation

Use procedural fur cues.

Higher quality may include shell/fin-style hints if they materially improve the look within the performance budget.

Do not sacrifice stability for elaborate fur.

## 10.5 GPU skinning

Add dedicated skinned shaders, including shadow support.

Use a joint palette within WebGL2 limits.

Ensure shader interfaces obey the pinned bgfx/shader compiler constraints.

## 10.6 Procedural locomotion

Player:

* speed-driven gait phase;
* stride/cadence relationship;
* pelvis bob and sway;
* counter-rotating arm swing;
* acceleration lean;
* turning lean.

## 10.7 Foot IK

Use two-bone IK.

Required behaviour:

* adapt feet to terrain;
* plant feet during stance;
* avoid visible sliding;
* adjust pelvis height for slope.

## 10.8 Player states

Implement:

* idle breathing;
* idle weight shifts;
* crouch;
* jump;
* landing squash;
* wading;
* gather interaction;
* kneeling at the fire;
* drinking;
* shivering when cold.

Transitions must be blended.

## 10.9 Look-at

Player head orientation should respond plausibly to:

* points of interest;
* camera direction.

Avoid unnatural snapping.

## 10.10 Wolf animation

Support:

* walk;
* trot;
* lope;
* spine flex;
* ear spring;
* tail spring chain;
* crouch-stalk;
* flee.

## 10.11 Transition quality

Use cross-fade or equivalent interpolation.

No visible pose popping.

## 10.12 Required tests

Test:

* skin weights sum to 1;
* no more than four influences;
* bind pose reproduces the rest mesh;
* IK solver converges;
* IK respects joint limits;
* foot drift remains below approximately 2 cm during stance at walk/run speeds on flat ground and slopes;
* no unacceptable pose discontinuity across state transitions;
* no NaNs during long randomized input runs.

Keep:

```text
?qa=character
```

as a close-up character screenshot scenario.

### M3 exit gate

Both player and wolf use the new skinned pipeline in the final rendering path.

Animation tests pass.

No known NaN, IK instability or major transition artifact remains.

# 11. Milestone M4 — balanced cinematic graphics pass

The purpose of M4 is high visual impact per unit of implementation complexity.

Do not turn M4 into an engine rewrite.

For every feature that is actually shipped:

* define Low/Medium/High behaviour;
* provide a capability fallback;
* preserve a sensible result when the high-quality path is unavailable.

A feature that is explicitly deferred does not need full Low/Medium/High implementation.

## Priority order

### M4.1 Atmosphere

Implement, where the hardware/capability budget allows:

* half-resolution screen-space sun shafts through mist;
* bloom using a sensible downsample/filter/upsample chain;
* improved height and valley fog;
* sun in-scatter;
* time-of-day grading presets:

  * dawn;
  * morning;
  * midday;
  * dusk;
  * night;
* filmic tone response.

Prefer stable approximations over expensive techniques that only work on one backend.

### M4.2 Ambient occlusion and contact

Use:

* affordable half-resolution SSAO or GTAO-lite on High;
* baked terrain/canopy AO on all quality levels;
* short character contact shadows on High.

### M4.3 Forest

Improve:

* pine crowns using volumetric-looking branch-cluster structure;
* fuller appearance from below;
* bent/darkened interior shading where useful;
* bamboo;
* hierarchical wind;
* trunk sway;
* branch motion;
* leaf flutter;
* valley-scale gust waves;
* distant tree impostors where beneficial;
* grass hue variation;
* grass height variation;
* grass clumping.

Avoid making grass uniformly lime.

### M4.4 Terrain

Implement material variation using:

* moss;
* rock;
* soil;
* leaf litter;
* wet stream banks;
* height blending;
* triplanar projection where appropriate;
* procedural detail normals;
* visibly darker/damper ground near water.

### M4.5 Anti-aliasing

Add:

* FXAA or SMAA-lite.

Add TAA only if it is genuinely stable on foliage and movement.

Do not ship visibly smeary TAA merely because it exists.

### Optional stretch work

Only after the required M4.1–M4.5 work is stable:

* water refraction;
* shore foam;
* campfire smoke;
* heat shimmer;
* distant mountain silhouettes;
* aerial perspective.

These are optional.

They must not destabilize the release.

## M4 deferral rule

M4 is impact-driven.

If stability, correctness or release completion is threatened:

* preserve the stable implementation;
* defer the lowest-impact remaining visual item(s);
* record the exact reason in `DESIGN_LOG.md`.

Do not force every visual effect into the release at the expense of the release itself.

## Performance budget

High should target approximately:

* Iris Xe class;
* Apple M1 class;
* 1080p.

Add:

```text
?bench=1
```

and:

```text
--bench
```

with a deterministic camera route through:

* day;
* dusk;
* night campfire.

Produce JSON frame-time statistics covering:

* CPU timing;
* bgfx GPU timing where available.

The Arena sandbox cannot measure a real GPU.

Therefore:

* SwiftShader measurements must be explicitly labelled SwiftShader/software;
* do not convert them into an Iris Xe/M1 claim;
* do not block the release merely because real hardware was not benchmarked.

After the release is ready, the owner may choose to run the benchmark on real hardware, but the agent may proceed without that measurement.

## M4 evidence

Capture before/after screenshots for the relevant QA scenarios.

CI-generated screenshots may be uploaded, but only screenshots actually inspected by the agent are described as visually inspected.

### M4 exit gate

The graphics pass is complete enough that the resulting improvement is clearly visible without introducing release-critical regressions.

Any deferred visual items are explicitly documented.

Commit and push M4.

# 14. Pull request, merge and release procedure

## 14.1 Open the PR

Push the session branch.

Create a PR:

```bash
gh pr create \
  --base main \
  --title "Mistpine v0.1.0: stability, graphics, animation, desktop + web releases" \
  --body-file <notes>
```

The PR body must contain a concise verification table.

Use the same evidence/honesty rules as this prompt.

## 14.2 Dry-run release on the PR head

Run the release workflow against the exact PR head SHA.

Use the workflow's dry-run mode so that final release assets are not uploaded.

Conceptually:

```bash
gh workflow run release.yml \
  -f tag=v0.1.0-rc \
  -f sha=<head-sha>
```

Then:

```bash
gh pr checks --watch
```

and inspect the release workflow result.

If anything fails:

* fix;
* commit;
* push;
* wait for updated CI;
* rerun the dry run as needed.

## 14.3 Owner approval gate — mandatory

When:

* the PR head is green;
* the dry-run release pipeline is green;
* all required release checks pass;

**STOP before merging.**

Ask the owner for explicit approval to merge the PR.

Do not run:

```bash
gh pr merge
```

until the owner explicitly approves.

Do not reinterpret silence as approval.

## 14.4 After explicit merge approval

Merge using:

```bash
gh pr merge <n> --merge
```

Record the merge SHA.

Create a draft release:

```bash
gh release create v0.1.0 \
  --target <merge-sha> \
  --draft \
  --title "Mistpine v0.1.0" \
  --notes-file CHANGELOG-excerpt.md
```

Build and attach release assets:

```bash
gh workflow run release.yml \
  -f tag=v0.1.0 \
  -f sha=<merge-sha>
```

Wait for the workflow to finish successfully.

## 14.5 Verify the draft release

Run:

```bash
gh release view v0.1.0 --json assets
```

Verify:

* every expected asset exists;
* asset names are correct;
* sizes are plausible;
* `SHA256SUMS.txt` contains all other release assets;
* no required asset is missing.

The Arena sandbox cannot download the assets because GitHub object storage is blocked.

Therefore verify release existence and metadata through GitHub.

Do not claim local execution of an inaccessible release artifact.

## 14.6 Publish only when verified

Publish only when:

* all release assets are present;
* all runner-side checks passed;
* required documentation is updated;
* no known release-blocking issue remains;
* the Pages deployment has succeeded where verifiable.

If a post-merge release problem occurs:

* fix forward with a new commit;
* rebuild the affected release artifacts;
* re-run validation;
* never publish a known-broken release.
